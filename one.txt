## Part 1: Context Manager (`src/ra_agent/context.py`)

### What to Say:

> "Let me start with the **Context Manager** - I like to think of this as the **memory** of my agent.
>
> Think of it like a whiteboard that can only hold 4000 tokens worth of information. The Context Manager decides what stays and what gets erased.
>
> It tracks three things: the user's original goal, the execution plan, and completed tasks. When we're planning, it only shows the goal. During execution, it shows the current task plus the last 3 completed tasks. This prevents token overflow while keeping the most relevant information.
>
> The magic happens in the truncation - search results get cut to 500 characters, URL content to 1000 characters. This keeps the LLM focused without losing critical context."

## Part 2: Executor (`src/ra_agent/executor.py`)

### What to Say:

> "Next is the **Executor** - this is the **action engine** of my agent. If the Context Manager is the memory, the Executor is the hands doing the work.
>
> Here's how it works: It takes the plan from the planner, loops through each task, and executes them one by one. For search tasks, it calls the search tool. For summarize tasks, it calls the LLM. For read tasks, it fetches URL content.
>
> What I love about this design is transparency. Every step is logged - you see exactly what the agent is doing. 'Executing task 1 of 3' - you know the progress. 'Searching for Python frameworks' - you know what it's looking for.
>
> After each task, it updates the context manager with the result. Then the next task can use that information. This creates a chain of reasoning - each step builds on the previous ones."

## Part 3: LLM Client (`src/ra_agent/llm.py`)

### What to Say:

> "The **LLM Client** is my **communication layer** to AI models. I designed this to be a thin wrapper - it just handles the API calls and nothing else.

> Currently it's configured for OpenAI, but notice how the rest of the code never touches OpenAI directly. This means I can swap providers easily. Want to use Ollama locally? Just change the base URL. Want to use Anthropic? Just modify this one file.

> This abstraction keeps the agent logic clean. The planner doesn't care HOW the LLM works, it just calls `llm.chat()` and gets a response."

## Part 4: Planner (`src/ra_agent/planner.py`)

### What to Say:

> "The **Planner** is the **strategy builder**. This is where vague user goals become concrete action plans.
>
> For example, 'Compare Python and JavaScript' becomes three specific tasks: search Python frameworks, search JavaScript frameworks, then summarize the comparison.
>
> The output is always JSON - structured, predictable, easy to parse. I force the LLM to output only JSON by using a strict system prompt.
>
> But LLMs can be unreliable, so I built fallbacks. If JSON parsing fails, it returns a simple two-task plan: search then summarize. If the LLM is completely down, it still gives the user something useful.
>
> Each task gets required fields - description, type, and query. The planner validates this before returning, so the executor never gets malformed tasks."

## Part 5: Prompts (`src/ra_agent/prompts.py`)

### What to Say:

> "The **Prompts module** is my **prompt library** - all the instructions the LLM receives live here.
>
> Why separate prompts from logic? Two reasons. First, it makes tweaking prompts easy - I don't need to dig through code to change wording. Second, it keeps the planner and executor clean - they just use `prompts.PLANNING_PROMPT.format(goal=goal)`.
>
> Each prompt has placeholders like `{user_goal}` or `{context}`. The code fills these in at runtime. This is how I keep prompts dynamic without string concatenation everywhere.
>
> The planning prompt includes examples - this is few-shot prompting. By showing the LLM what good output looks like, I get much more reliable JSON responses."
